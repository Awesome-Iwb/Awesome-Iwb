# 文档架构设计说明 (DESIGN)

## 设计目标

本次重构将原始的单文件 README.md（约 293KB）拆分为多文件结构，核心目标是：

1. **分离数据与视图**：让数据可以独立维护和程序化访问
2. **降低维护成本**：分类和标签统一管理，修改一处即可全局生效
3. **提升可读性**：通过多文件拆分让每个文档专注单一职责
4. **便于扩展**：新项目只需追加 JSON 数据，无需调整 Markdown 布局

## 文件结构设计

```
根目录/
├── README.md              # 主索引：项目介绍 + 分类总览 + 项目详情
├── CONTRIBUTING.md         # 贡献指南：如何参与项目贡献
├── _data/
│   └── project.json        # 核心数据：所有项目、分类、标签、贡献者
└── docs/
    ├── install.md          # 安装与配置指南
    ├── usage.md            # 使用说明与最佳实践
    └── DESIGN.md           # 本文档：架构设计说明
```

| 新分类 | 数量 | 说明 |
|--------|------|------|

### 分类合并理由

1. **屏幕批注与白板（合并屏幕书写 + 视频展台）**
   - 视频展台类只有 ShowWrite 一个项目，单独成类过于单薄
   - ShowWrite 本身也具备屏幕批注功能，功能上高度重叠
   - 合并后用户在一个分类中就能找到所有屏幕相关工具

2. **课表与日常看板（合并课表类 + 看板类）**
   - 原「看板类软件」中很多项目兼具课表功能（如 ClassIsland 的看板属性）
   - 两个分类的边界模糊，用户在查找时需要跨分类翻阅
   - 合并后按「信息展示」这一共同点统一组织，更符合实际使用场景

3. **考试专题工具（独立保留）**
   - 考试场景有明确的时间性（期中/期末），使用频率和使用方式与日常看板截然不同
   - ExamAware 组织形成了独立的项目生态

4. **教学辅助与效率工具（保留并扩展）**
   - 该分类覆盖面广、项目量大，不宜进一步拆分
   - 合并会使单一分类过于庞大，保留现有规模

## 数据结构设计考量

### 为什么要把数据和视图分离到 JSON 和 Markdown 中

1. **单一数据源（Single Source of Truth）**
   - 所有项目的名称、开发者、标签等信息只存储在 `project.json` 中
   - README 中的标签和数据声明来源于 JSON，避免数据不一致

2. **程序化可访问**
   - JSON 格式可被任何编程语言直接解析
   - 未来可以基于 JSON 构建动态网站、API 接口或 CLI 工具
   - 便于自动化工具进行数据校验（如检查必填字段）

3. **降低维护门槛**
   - 新增项目只需在 JSON 中追加一条记录
   - 修改项目信息只需改 JSON 一个地方
   - 分类重组只需调整 JSON 结构，Markdown 文档同步更新

4. **团队协作友好**
   - JSON 的 diff 比 Markdown 表格更清晰
   - 可以在 CI/CD 中加入 JSON Schema 校验
   - 减少因 Markdown 格式错误导致的合并冲突

### 字段设计原则

每个项目包含三个核心必填字段及多个扩展字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | string | **必填** - 项目名称 |
| `developer` | string | **必填** - 开发者名称 |
| `category` | (由父级指定) | **必填** - 分类归属 |
| `repo` | string | GitHub 仓库路径 |
| `language` | string | 主要编程语言 |
| `status` | string | 维护状态（active/archived） |
| `tags` | array | **标签数组（不硬编码）** |
| `contributors` | array | 项目贡献者列表 |
| `organization` | string | 所属组织 |

## 标签不硬编码的实现

在 README.md 中，每个项目的标签明确标注「来源于 _data/project.json」，标签内容与 JSON 中的 `tags` 数组严格一致。修改标签时只需更新 JSON 文件，Markdown 文档随之更新。

## 方案优势总结

1. **可复制性**：JSON 数据结构标准化，其他 Awesome 列表项目可直接复用
2. **扩展性**：新增字段（如「官网链接」「下载地址」）只需扩展 JSON schema
3. **自动化潜力**：可配合 GitHub Actions 实现数据校验、自动生成 README 等
4. **国际化潜力**：未来可扩展为多语言 JSON 文件，按语言加载不同数据
5. **保持兼容**：Markdown 仍然是 GitHub 渲染的载体，不影响现有浏览体验
