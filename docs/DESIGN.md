# 设计说明

## 整体设计思路

本次重构的核心目标是将原先单文件、混合数据与展示的 README.md 拆分为清晰的多文件结构，实现**数据与视图分离**，让项目更易于维护和扩展。

最终产出六份文件：

| 文件 | 职责 |
|------|------|
| `_data/project.json` | 纯数据层：所有软件项目的结构化存储 |
| `README.md` | 主入口：项目介绍 + 分类标签（标签引用自 JSON） |
| `CONTRIBUTING.md` | 贡献指南 |
| `docs/install.md` | 安装指引 |
| `docs/usage.md` | 使用指南 |
| `docs/DESIGN.md` | 本文档：设计说明 |

## 分类设计

原始文档有 **8 个分类**：屏幕书写、第三方视频展台、课表类软件、看板类软件、考试看板系列、ClassIsland 插件、随机点名类、辅助类软件和实用工具。

重构后合并为 **5 个分类**：

| 新分类 | 合并来源 | 设计理由 |
|--------|---------|---------|
| 屏幕批注与白板 | 屏幕书写（原封不动） | 更准确描述功能场景 |
| 课程管理 | 课表类软件 + ClassIsland 插件 | 课表与插件本质上是同一生态的上层应用和扩展，合并更自然 |
| 信息展示与看板 | 看板类软件 + 考试看板系列 | "考试看板"和"日常看板"只是看板的应用场景不同，底层功能一致，合并不产生歧义 |
| 课堂互动 | 随机点名类（重命名） | 原名过于狭隘，"课堂互动"为后续更多类型工具留出空间 |
| 系统工具与辅助 | 辅助类软件 + 第三方视频展台 | 视频展台本质也是一体机辅助工具，放在独立分类中过于突兀 |

**删除的类别**：无。所有类别均通过合并或重命名保留，未丢失任何原有内容。

## 数据结构设计

### 为什么 JSON + Markdown 分离？

原始文档将软件数据（名称、开发者）与 Markdown 排版混合在一起。向列表中添加一个新项目需要：

1. 找到正确的 Markdown 表格位置
2. 插入一行，手动对齐所有列
3. 更新分类统计徽章

这种方式的维护成本随项目数量线性增长。

重构后将数据抽取到 `_data/project.json`：

```json
{
  "categories": [
    {
      "id": "screen-annotation",
      "name": "屏幕批注与白板",
      "projects": [
        { "name": "Ink Canvas Plus", "developer": "Clover Yan" }
      ]
    }
  ]
}
```

数据结构仅包含三个核心字段：
- **分类**（category）：`name` 字段存储分类名称
- **项目名称**（name）：软件的名称
- **开发者**（developer）：软件的主要作者

额外保留 `id` 和 `description` 字段用于程序化引用和跨页面展示。

### 优势

1. **可机器读取**：JSON 格式可被脚本、GitHub Actions、前端页面直接解析
2. **单一事实来源**：项目列表只在一个文件中维护，杜绝数据不一致
3. **易扩展**：新增字段（如 GitHub stars、截图链接、官网地址）只需在 JSON 对象中添加键值对
4. **便于自动化**：可编写脚本自动检查死链、统计分类数量、生成徽章、同步到外部系统

## 扩展与维护

### 添加新项目

只需在 `_data/project.json` 的对应分类下添加一行 JSON 对象：

```json
{ "name": "新软件", "developer": "作者名" }
```

无需触碰任何 Markdown 文件中的表格或标签。

### 新增分类

在 `categories` 数组中添加新对象，包含 `id`、`name`、`description` 和 `projects` 字段即可。README.md 会自动渲染新分类。

### 生成 README 标签

README.md 中的分类标签不再硬编码，而是声明式地引用 JSON 数据。当 JSON 变更时，标签内容跟随变化，保持数据与视图的一致。

### 未来可能的方向

- 添加 `url` 字段存储项目主页/GitHub 链接
- 添加 `tags` 字段用于多维度检索
- 通过 GitHub Actions 自动校验 JSON 结构和去重
- 生成静态站点展示所有项目
